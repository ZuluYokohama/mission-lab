# Runtime and evidence contract

The authoritative validators live in `core.py`, `planner.py` and the executor. This document explains their intent; it does not relax runtime validation.

## Mission

`schema_version` is 1. `mission_id` is an identifier. Each requirement has a unique `id`, nonempty `text`, a nonempty list of `acceptance_criteria`, and an `evidence_refs` list. Each unresolved item contains `id`, `question`, and `affects`, where `affects` is intent, acceptance, authority or tradeoff. Each of one to eight file inputs records `id`, `path`, `size_bytes` and lowercase 64-character SHA-256.

Runtime records reject duplicate JSON keys, unknown fields, malformed identifiers, non-finite numbers and Boolean values passed as integer bounds. Inputs are identity checked against actual file size and bytes for execution planning. Archive metadata inventory is a separate operation and performs no content hash.

An explicit graph, when supplied, must agree with registered semantics and contains 1 to 2048 nodes. 2048 covers the closed hash, reference, verification and manifest nodes of an eight-input mission and additional `llm:grok` and `gate` nodes. A gate counts toward that cap. Ancestor checks are quadratic on a long chain, so the cap is a bound on that work, not a measured throughput. Inputs remain 1 to 8. Each node declares `id`, `operation`, `depends_on`, `outputs`, `state_reads`, `state_writes`, and an `input_id` when required. An `llm:grok` node may omit `input_id` when it carries inline prompt text. A `gate` node has no `input_id`. Each node owns one output; state reads require producer ancestry. Every input requires exactly one primary hash, reference hash and verification. One manifest covers all verifications and its dependencies stay exactly those `verify_digest` nodes. A gate output is not a verified-artifact row, and the manifest cannot depend on a gate. `llm:grok` and `gate` do not replace that path. A graph compiled because the mission omitted `tasks` stays hash-only. Cycles and unknown references fail closed.

## Registered operations

| Operation | Candidate role | State contract |
|---|---|---|
| `sha256` | Whole-file or bounded streaming implementation | Reads the declared immutable file; emits digest and byte count |
| `reference_sha256` | Separate fixed 8 KiB read path | Reads the same declared file; emits comparable digest and byte count |
| `verify_digest` | Compare candidate, reference and declared identity | Reads both producer outputs; emits a passed verification only on agreement |
| `assemble_manifest` | Aggregate verified artifacts | Reads every verification; emits the final artifact manifest |
| `llm:grok` | One chat-completions call, or one local fixture read | Reads a prompt and optional fixture; emits a receipt and hash-addressed response artifacts |
| `gate` | One closed predicate over dependency receipts | Reads those receipts in the controller; emits pass, fail, indeterminate, or pending |

The reference is a separate registered execution path using standard-library hashing, not an independent SHA-256 library or a human reproduction. Candidate and operator revisions are explicit; unsupported revisions fail validation. `llm:grok` has one candidate, `chat_v1` revision `1`. Its schedule estimate is `fixed_task_ns`. Observed latency is a separate receipt field and is not a measured model duration. `gate` has one candidate, `predicate_v1` revision `1`. The schedule still assigns that node a worker slot and `fixed_task_ns`. That figure is an estimate. Execution does not start a process, does not write a process observation, and does not reserve a read buffer or a model budget for the gate.

## Registered chat call

`llm:grok` declares `model`, `max_output_tokens`, `temperature`, `timeout_seconds`, `max_response_bytes`, and `transport`, plus exactly one of inline `prompt` or a prompt-file `input_id`. Unknown fields are rejected. `model` matches `grok-` followed by 1 to 64 characters from `[A-Za-z0-9._-]`, and the first of those characters is alphanumeric. That pattern is a naming bound. It does not state that the named model is available or suitable. `max_output_tokens` is an integer from 1 to 4096 and is sent as `max_tokens`; it is not a local measurement of output bytes. `temperature` is a multiple of 0.01 in [0, 2]. A Boolean is rejected, and a whole number is stored as an integer. `timeout_seconds` is finite and in [0.1, 120], and must be at least one second below the profile timeout so a socket timeout can be recorded before the executor kills the worker. `max_response_bytes` is an integer from 1 to 65536.

Inline prompt text is 1 to 4096 UTF-8 bytes and contains no NUL. A prompt file is a mission input of that same size. Transport is `xai` or `fixture`. The mission cannot name a URL. Transport `fixture` requires `fixture_id`, a different mission input of 1 to `max_response_bytes` bytes containing one chat-completions JSON object. The node's dependencies include the `verify_digest` nodes of the prompt file and, when present, the fixture file. Any further dependency must be a `gate`. An inline prompt with transport `xai` may depend only on gates, and otherwise has an empty dependency list. `state_reads` must match those outputs. A gate is not a substitute for the file verification.

Transport `xai` posts compact sorted JSON to `https://api.x.ai/v1/chat/completions` with `urllib`. The body is `model`, one user message, `max_tokens`, `temperature`, and `stream` false. The bearer token is the worker environment variable `XAI_API_KEY`, exact spelling. That name must be granted to the task. A fixture task, and any task that is not this operator on transport `xai`, cannot receive it. An unset grant fails before process start. The worker does not write the key into the receipt or the stored response. Transport `fixture` reads the declared file, records HTTP status 200, and does not open a socket or read `XAI_API_KEY`.

`SSL_CERT_FILE`, `SSL_CERT_DIR`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY` are not platform start names. A task that needs one must grant it. urllib will use a granted proxy, and that proxy can see the bearer token. Redirects are refused, so `Authorization` is not followed to another host. A timeout, a non-2xx status, malformed JSON, or a body over the declared cap fails the task. The read keeps at most the cap; one extra byte detects overflow and is discarded.

A successful receipt records the model id, transport, request parameters, prompt hash and byte count, request-body hash, response-body hash and size, HTTP status, latency in nanoseconds, provider-reported `prompt_tokens`, `completion_tokens`, and `total_tokens`, the response model string, finish reason, and the hash and size of the assistant text. It does not record prompt text, the key, or the assistant text. The response body is stored at `llm_responses/<sha256>` and the assistant text at `llm_content/<sha256>`. Success requires HTTP 200, one choice, an assistant string, a printable-ASCII finish reason of 1 to 64 characters, a printable-ASCII response model of 1 to 128 characters, and non-negative integer usage fields of at most 1e9. Extra usage fields are ignored and not recorded.

The read-buffer reservation is the larger of the prompt-file size and the fixture-file size, or zero when the prompt is inline and transport is `xai`. The response cap is not added to that reservation. Prompt and fixture inputs are copied into the run input snapshot so replay does not reread the live files. Replay rebuilds the request bytes, checks the recorded hashes against the archived response and content, and, for a fixture, checks that those response bytes equal the archived fixture. It does not call the network.

A unit test may pass `urllib_chat` a loopback `http://127.0.0.1` URL. That argument is not a mission field. The optional live smoke test runs only when `MISSION_LAB_GROK_LIVE=1` and `XAI_API_KEY` is set. CI does not set that flag and does not need a key. The receipt does not score quality, truth, or fitness of the response.

## Merit gates

A `gate` node depends on 1 to 32 upstream nodes and declares one `predicate`. Unknown extra fields are rejected. The predicate is a closed object. It is not Python source, and it is not evaluated with `eval`, `exec`, or the `re` module. Normalization rejects an unknown kind, a cycle through the gate's own dependencies, and a reference that is not a direct dependency.

`digest_equal` names 2 to 8 dependencies. The stored list is sorted. It compares `sha256` and `size_bytes`. It cannot name a gate. Agreement is pass. Disagreement is fail. A missing digest or byte count is indeterminate, including when the named node is `llm:grok` and those fields are absent.

`llm_field` names one `llm:grok` dependency and one of `response_sha256`, `content_sha256`, `request_sha256`, `finish_reason`, `response_model`, `transport`, or `model`. It declares `equals` or `pattern`, not both. `equals` is printable ASCII of 1 to 256 characters. A pattern is 1 to 128 characters and at most 32 atoms. An atom is a literal or `:hex:`, `:alnum:`, `:digit:`, or `:any:`. A quantifier is `{n}` or `{n,m}` with each bound an integer from 0 to 64 and no leading zeros. The match is the whole string. `*+?()|^$\[]` are rejected. This is not a regular expression and not a claim about model quality.

`numeric_bounds` declares an integer `minimum`, `maximum`, or both, from -2^31 to 10^18. A Boolean is rejected. Reversed bounds are rejected. `prompt_tokens`, `completion_tokens`, `total_tokens`, `latency_ns`, `http_status`, `response_bytes`, `content_bytes`, and `spend` require an `llm:grok` dependency. Token fields are the receipt's `usage` integers. `spend` is the settled model-account actual; without a settled account it is indeterminate. `exit_code` is the recorded worker observation and cannot name a gate. A missing number is indeterminate. A number outside the declared bounds is fail.

`all` and `any` contain 1 to 16 children. Nesting stops at depth 8, and one gate holds at most 32 predicate nodes. Every child is evaluated. For `all`, fail wins, then indeterminate, then pending, then pass. For `any`, one pass is enough; otherwise indeterminate wins, then pending, then fail. `human_approval` appears at most once and names an `approver_id`. Reasons are capped at 200 characters.

The gate receipt is `schema_version`, `gate_id`, `outcome`, `reason`, and `predicate_sha256` of the normalized predicate. Outcomes are `pass`, `fail`, `indeterminate`, and `pending`. The task status is `succeeded` when evaluation finishes, including when the outcome is not pass. An `evaluated` event records that outcome. There is no process observation.

A dependency that is a gate launches downstream work only when its outcome is `pass`. Fail, indeterminate, and pending set each downstream task to `blocked`, set `blocked_by` to the sorted gate ids, and set the error to `Blocked by gate` plus those ids. Those tasks are not started. When a model budget exists, their account state stays `unlaunched` and they are not added to accounted cost. The gate itself reserves zeros with `input_bound` `none` and stays `unlaunched`. A failed non-gate dependency still blocks with `A dependency did not succeed` and does not invent a gate id.

A run is accepted only when every task status is `succeeded` and every gate outcome is `pass`. A finished gate that did not pass does not promote `manifest.json`.

Replay recomputes every gate with the same function from archived outputs, settled accounts, recorded exit codes, and `approvals.json`. The archived receipt must equal that result, including `predicate_sha256`. A changed predicate or a changed outcome is rejected. Replay does not call the network, does not start a worker, and is not a second implementation.

`human_approval` reads `approvals.json` in the run directory. One file is used so a gate id may contain `:`, which is not a legal Windows file name. A record has `schema_version` 1, `gate_id`, `approver_id`, and `approved_at` as `YYYY-MM-DDTHH:MM:SSZ`. The calendar date is checked. The timestamp is not compared with the clock and is not a signature. No record is pending, and pending blocks downstream. A malformed file makes every such gate indeterminate. A record that names a different gate or approver is fail. A matching record is pass, and the reason states that the record is not authenticated. Signed receipts are not implemented. `resume --run --out --approval` checks the sealed prior run, copies one record into a new run directory, and executes the same plan again. It does not reuse worker processes and does not rewrite the prior run. `resume_of` stores that plan id and the prior semantic sha256. `human_review` on the plan stays false.

A revision trigger of kind `gate_evidence` requires `evidence_refs` that name gates on the prior plan. `gate_evidence_trigger` fills those refs from receipts whose outcome is fail, indeterminate, or pending. The replacement mission may tighten a predicate, and the resource profile may change so a `sha256` candidate swaps. The report lists the trigger, the evidence refs, and the changed tasks. The trigger does not by itself rewrite the predicate. `fixtures/mission_gate.json` is a fixture-transport mission that runs one gate. It does not use the network or an API key, and passing that gate is not a quality score.

## Resource profile and estimates

Fields are `schema_version`, `workers`, `read_buffer_bytes`, `timeout_seconds`, `estimate_origin`, and optional `cost_model`, `worker_env`, and `model_budget`. Worker slots are 1..8. Read-buffer reservation bytes are 1..2^40. Timeout seconds must be finite, positive and at most 3,600. Cost origins are `injected_fixture` or `measured`; measured profiles require explicit supplied costs.

The cost model declares whole, stream and reference nanoseconds per byte plus fixed task nanoseconds. Defaults are injected illustrative costs. Supplying a measured label does not independently authenticate the measurement; provenance must substantiate any scientific interpretation. Estimated schedule duration and actual wall-clock observations remain separate fields. The nanosecond cost model is not a model-call budget.

The executor bounds its worker count and sum of registered read-buffer reservations. Whole-file reservations depend on input size; streaming and reference paths have registered chunk bounds. An `llm:grok` reservation is only the declared prompt or fixture bytes. These bounds exclude interpreter and library overhead, incidental metadata/state allocations, process RSS, OS caches, cores, GPU allocations, response bytes beyond the separate cap, and energy.

## Model budget

`model_budget` is optional. A profile that omits it does not reserve, settle, or record model requests, tokens, or spend. The duration `cost_model` is unchanged in that case.

When present, the object is closed. Required fields are `max_requests` (0..10,000), `max_spend` (0..10^18), `unit`, and `prices`. Optional caps are `max_output_tokens` and `max_total_tokens` (each 0..10^12). An omitted token cap is not enforced. `unit` matches `^[a-z][a-z0-9_-]{0,31}$`. It names the fixed-point unit the profile is counting. It is not a currency conversion, a market rate, or an invoice.

`prices` contains 1..32 model ids. Each row is `input`, `output`, and `per`. The prices are integers from 0 to 10^12. `per` is `token` or `million`. There is no built-in price. A model id that an `llm:grok` task uses and that the table does not list fails planning. For `per` `million`, each side is `ceil(tokens * price / 1_000_000)` using integer arithmetic. The two sides are summed. A partial million is not free. The sum must fit in 0..10^18 or planning fails.

An `llm:grok` task reserves one request. Its input-token bound is `max_input_tokens` when the node declares it, and otherwise the UTF-8 byte length of the inline prompt or the declared size of the prompt file. One token per byte is a reservation ceiling, not a tokenizer measurement. A declared `max_input_tokens` must be an integer from 1 to 10^9 and at least that byte length; a smaller declaration is rejected. Output tokens reserve `max_output_tokens`. Total tokens reserve the sum of those two bounds. Spend reserves the price of that input bound and that output bound. Other operations reserve zeros. A gate's reservation is those zeros with `input_bound` `none`, and the gate is not launched, so its account state is `unlaunched` rather than settled. A task blocked by a gate that did not pass is also `unlaunched` and is not charged. The reservation is stored on the binding.

Planning admits a task only when its own reservation fits every declared cap, including equality. It then admits a schedule only when the sum of those reservations still fits, because settlement can only reduce a hold. A profile that cannot reserve every task has no execution plan. The errors name the task or the model budget. No partial plan is emitted.

Before each launch the executor adds the task reservation to the running accounted total, which is settled usage plus holds still outstanding. If that projection exceeds a cap, the task is not started. Its status is `blocked`, the account state is `refused`, and the error names the task. The hold is not charged. After a successful receipt, provider-reported `prompt_tokens`, `completion_tokens`, and `total_tokens` are priced with the same rule. Each of those counts, the derived spend, and the one request must be less than or equal to the reservation. The hold is then replaced by that actual usage. If the receipt exceeds the reservation, or the task fails, times out, or is aborted after launch, the receipt is not settled and the worst-case hold stays charged. Accounted cost therefore does not record a usage figure above the hold, and it does not drop a launched call to zero when no fitting receipt exists. A launch that fails before the process starts releases the hold. A failure after the process exists keeps the worst-case hold charged, including a failure to watch that process, and replay requires that charge.

The run records the reservation, the actual usage when settled, and the account state on each task and on each launched observation. Events carry the running accounted total. The semantic record stores the caps, the profile prices, per-task rows, and reserved, actual, accounted, and remaining totals. Remaining is the cap minus accounted, for each declared cap. The report renders those rows. Replay recomputes the reservation from the plan, recomputes settled usage from the archived receipt, and walks the event ledger. A mismatch fails. Replay does not call the network and does not supply a missing usage figure.

This ledger is an accounting bound on declared reservations and provider-reported counts. It is not a provider invoice, a payment authorization, a measurement of energy, or proof that a charged hold matches an unseen bill. A call that fails before a receipt, or whose reported usage exceeds the reservation, keeps the hold and does not reconstruct a larger usage number.

## Planning

The list scheduler is the same for both planner versions. Ready tasks are ordered by descending estimated critical-path tail, then task id. A task starts only when a worker slot is free, the sum of active read-buffer reservations fits, and the running sum of model reservations fits. That sum is not released at task completion. Equality with a declared cap fits. A per-task candidate whose own buffer or own model reservation exceeds a cap is dropped before scheduling. If none remain, planning names the task and emits no plan. Timeouts stay in the `llm:grok` check: the request timeout must be at least one second below the profile timeout.

Planner `coordinate-list-v2` version `2` is the default. The plan records that stamp. It does not build the Cartesian product of candidates. It starts from three deterministic seeds, in order: shorter estimated duration, then smaller read-buffer reservation, then candidate id; smaller read-buffer reservation, then shorter duration, then candidate id; candidate id alone. From each distinct seed it tries every one-candidate change and every two-candidate change. It keeps a change only when that change is strictly better than that seed's current assignment, then repeats for at most eight improving passes. The recorded plan is the best key among those walks. A later seed may step through a key that is worse than an earlier seed. The key is estimated makespan, then the sum of estimated durations, then the tuple of candidate ids in node-id order. `enumerated_bindings` is the number of distinct admitted vectors for which this search constructed a schedule. It is not the size of the product. The same mission, resources, sources and planner version produce the same plan bytes and the same `plan_id`.

Worker-environment grants remain limited to 64 tasks. A larger graph can still contain tasks that receive no grant. A task that needs a grant and does not have one fails closed.

Only `sha256` has two registered candidates. With at most eight inputs there are at most eight such nodes. The walk above is quadratic in that count per pass, times a fixed pass cap and three seeds, times one list schedule. It is not an exponential enumeration of the graph. The list schedule itself walks the DAG with indegree counts. No speedup factor is stated here. The scaling test in `tests/test_planner.py` plans one synthetic graph of 2048 nodes and fails if that call exceeds 20 seconds in the test process.

This search can select a different valid binding than full enumeration. That can happen when every better key changes three or more `sha256` candidates at once and no one- or two-candidate change improves the key, or when a seed would need more than eight improving moves. The plan it returns has still passed the per-task filters and the schedule checks above. On the registered candidates a model reservation does not depend on the `sha256` candidate, and every candidate kept after the per-task buffer filter fits the read buffer by itself. The sum of reservations is therefore the same for every vector. If that sum exceeds a cap, schedule construction raises the model-budget error and no plan is emitted. A seeded test compares version 2 with full enumeration on small graphs. That sample is not a proof for every graph.

A plan with no `planner` field is replayed as planner v1. v1 still enumerates every admitted combination and still records the enumeration sentence in `schedule_algorithm`. v1 refuses a graph larger than 64 nodes, which is the cap it shipped with. A new plan is version 2. Replanning a v1 plan validates that plan with v1 and writes the replacement with v2. Adding the planner stamp changes `plan_id` even when the bindings and schedule match a v1 result, because the stamp is inside the plan hash. Source bytes are inside that hash as well.

## Worker environment

Registered workers do not inherit the controller process environment. The default is deny. For each launch the executor builds a new mapping with three parts:

- platform start names that are already set on the controller, limited to names used to start CPython and locate imports
- `PYTHONDONTWRITEBYTECODE=1` and `PYTHONUNBUFFERED=1`, set by the controller rather than copied
- names the resource profile grants to that task, copied from the controller when they are set to strings

On POSIX the start names are `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `PATH`, `PYTHONCOERCECLOCALE`, `PYTHONHOME`, `PYTHONIOENCODING`, `PYTHONNOUSERSITE`, `PYTHONPATH`, `PYTHONSAFEPATH`, `PYTHONUTF8`, `TMPDIR` and `TZ`. On Windows they are `APPDATA`, `HOMEDRIVE`, `HOMEPATH`, `LOCALAPPDATA`, `PATH`, `PATHEXT`, `PYTHONCOERCECLOCALE`, `PYTHONHOME`, `PYTHONIOENCODING`, `PYTHONLEGACYWINDOWSFSENCODING`, `PYTHONLEGACYWINDOWSSTDIO`, `PYTHONNOUSERSITE`, `PYTHONPATH`, `PYTHONSAFEPATH`, `PYTHONUTF8`, `SYSTEMDRIVE`, `SYSTEMROOT`, `TEMP`, `TMP`, `USERPROFILE` and `WINDIR`. A name is omitted when it is unset. The authoritative lists are `platform_env_names()` and `FORCED_WORKER_ENV` in `core.py`. Windows matches allowlist, grant, and reserved names without regard to case, and the executor passes and records those names in uppercase, the spelling CPython reports for the child. A case variant cannot grant a reserved name or copy a variable that was not granted.

Optional `worker_env` contains `declared` and `grants` only. `declared` is a list of at most 32 environment names. `grants` maps at most 64 task ids to nonempty lists of at most 32 of those names. Validation rejects undeclared names, duplicate names, malformed names, embedded values, names that collide with the platform or forced sets, unknown fields, and grants whose task id is not in the executable graph. A declared name that no task is granted is not copied. An unset or non-string granted name fails that task before a process is created; an empty string is not substituted.

Plans and resource profiles record grant names, not values. Plan normalization does not depend on the host operating system. Each launch event and task observation records sorted `environment_names` and no values. Replay rejects a receipt that names a variable outside the two platform lists, the forced flags, and that task's grants, or that omits a granted name or a forced flag. It also rejects an observation whose names differ from the launch event, and a receipt that repeats one name under another case. Name comparison folds case, so a Windows record can be replayed on POSIX. That check does not prove which platform names were set or the exact spelling a child reported, and it does not observe the child process.

This is process-environment filtering for the registered worker command. It is not a system-call sandbox, a credential store, or a statement that a worker which received a grant cannot disclose that value. TLS trust stores, proxy names, service endpoints, and `XAI_API_KEY` are outside the start allowlist. `llm:grok` with transport `xai` must be granted `XAI_API_KEY`. A granted proxy can see that token.

## Identity, output authority and replay

Plans record source hashes and a canonical content identity. Inputs and source code must retain their identities before execution. Plans, revisions and evidence outputs use fresh directories confined beneath package `evidence/`. Parent records are retained; earlier evidence is never overwritten. Symlink/junction traversal and unsafe output locations are refused.

Retained run evidence binds outputs, observed status and elapsed times to a plan. Replay validates identities and reconstructs predicates from those retained records. A successful replay is evidence-integrity validation, not a new execution measurement. Missing, malformed or altered observations must fail rather than be synthesized.

## Archive inspection

The public-release inventory root is the package fixture directory. Mission input paths are confined to the checkout and package fixtures. Descendants may be inspected. A keyword-only `allowed_roots` seam exists for Python unit tests and is absent from the CLI. Files cannot be used as inventory roots. All encountered reparse points are refused conservatively, even if their targets would remain in the archive.

`max_entries` counts files and directories and is 1..100,000. `max_depth` is 1..64. At a limit, `complete` is false and reasons are retained. Records contain relative path, kind, observed bytes for files, UTC modification time, extension and depth. The snapshot is non-atomic and cannot prove source integrity, lineage, executability, scientific validity or total counts when truncated. It reads no archive contents.

## Human and external boundaries

The code cannot resolve unclear intent, confer account permissions, establish human review, or issue arbitrary shell commands. It does not load local weights, train a model, mutate an external connector, publish, or edit its own source. `llm:grok` records one remote chat call or one local fixture read under the bounds above. A `gate` compares declared receipt fields. Passing one is not a quality score and does not set `human_review`. `human_approval` stores an approver id and a timestamp; that file is not a signature and not an account permission. Existing frozen research packages are not imported or changed.
